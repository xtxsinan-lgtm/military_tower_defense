## 1. T3 重要设计选择（逐条决定）

> 每条：背景（引用 GDD / 数值表）→ 选项 → 推荐 → 能否用 D3/D4 Python 纸面模拟器验证 → 批准后改动的文件。

### B-T3-01 交换比的"潜在损失"公式（03 与 05 的假设互相矛盾）

- 位置：03 §8.1 Q-X1、Q-I4、Q-X2；05 §8.1 `trust.exchangeBands`、`trust.wastefulWeapon`、`trust.minShotCostForExchangeMusd`，§8.2 Q-E2；数值表 §4 第 1 条。
- 背景：GDD 9.3「交换比 = 被拦截目标的潜在损失 ÷ 拦截弹价格」「用 PAC‑3 打 Shahed → 信任度下降并触发质询」；GDD 9.7 第 6–13 关「交换比压力最大」，是四大支柱之一的经济核心。数值表 §4 举例「PAC‑3（4 M$）打 Shahed（0.05 M$）」——用的是**敌方单价**。
- 问题：03 默认 `潜在损失 = 伤害等级 × 1 M$ × 保护目标权重`；05 的 `wastefulWeapon`（"比值 < 0.1"，注释"PAC‑3 打 Shahed 4/0.05 ≈ 0.0125"）却是按**敌方单价**设计的。两者放在一起时，按 03 公式（data：Shahed 伤害 3、Kh‑101 伤害 7、伊斯坎德尔‑M 伤害 8）：
  | 组合 | 03 公式 | 敌方单价 | 混合（推荐） |
  |---|---|---|---|
  | PAC‑3 → Shahed | 3/4 = 0.75（−1，**永远不触发"浪费"**） | 0.0125（−3） | 0.4/4 = 0.1（−3） |
  | Gepard 一次射击 → Shahed | 3/0.01 = 300（+3） | 5（+1） | 40（+3） |
  | PAC‑3 → Kh‑101 | 7/4 = 1.75（**−1**） | 3.25（0） | 13/4 = 3.25（0） |
  | NASAMS → Kh‑101 | 8.2（+1） | 15（+1） | 15（+1） |
  | PAC‑3 → 伊斯坎德尔‑M（对权重 1 目标） | 2（0） | 0.75（**−1**） | 12.8/4 = 3.2（0） |
  03 公式下"PAC‑3 打 Shahed"与"PAC‑3 打 Kh‑101"得分相同，交换比失去区分度；纯敌方单价下"用唯一能打弹道导弹的 PAC‑3 打伊斯坎德尔"反而扣分。
- 选项：
  - **A 伤害等级线性**（03 默认）：实现简单、体现目标价值；但区分度差（见上表），且 05 的浪费阈值必须重写。
  - **B 敌方单价 `costMusd`**（数值表 §4 举例的口径）：数据现成、直观；但滑翔炸弹 / Oreshnik 为 null，且弹道导弹的"正确用法"会被扣分，与 GDD"用对武器"的意图相反。
  - **C 混合（推荐）**：`潜在损失 = max(敌方单价, 2^(伤害等级−1) × lossMusdBase × 目标权重)`，`lossMusdBase = 0.1`（等级 3 → 0.4 M$、7 → 6.4、8 → 12.8、9 → 25.6、10 → 51.2），不以保护目标为目标时权重 1，诱饵 0，平台 `platformPotentialLossMusd = 10`。指数曲线对应数值表 §3.2 中伤害 9–10 "区块损毁"的跳跃；`max` 保证昂贵导弹不被低估。
- 推荐：**C**；同时把 05 的 `wastefulWeapon` 阈值改为按 C 公式标定（PAC‑3 → Shahed = 0.1，阈值取 `< 0.2`）。
- D3/D4 验证：**可以**。D4（战役纸面模拟）输入典型交战组合表，检查三条：便宜打便宜为正、PAC‑3 打 Shahed 必为最低档、PAC‑3 打弹道 / 巡航不为负。
- 批准后改动：03 §3.8 交换比与 Q-X1；05 §1.2 `trust.exchangeBands` / `wastefulWeapon` 的注释与阈值、§3.4；`data/rules/economy.json`（新增 `exchange { lossMusdBase, platformPotentialLossMusd }`）；数值表 §4 第 1 条补一句"潜在损失按 max(敌方单价, 伤害价值) 计"；GDD 不改。

### B-T3-02 多个火力单元同时可打一个目标时的分配策略

- 位置：03 §8.1 Q-E9（另见 03 §3.2、`TargetPriorityMode`）。
- 背景：GDD 5.1 空袭阶段是"自动交战"、部署阶段才是主要决策（约 70%）；GDD 9.3 交换比压力。分配规则决定"玩家放了便宜武器后，系统会不会先用它"，直接决定交换比是否可控。
- 选项：
  - **A 按火力单元 ID 升序贪心**（03 默认）：最简单；但"先部署的单位先开火"对玩家不可见，PAC‑3 若先部署就会抢先打 Shahed，玩家只能用交战规则逐个禁止。
  - **B 便宜优先（推荐）**：同一步内对同一目标，候选火力单元按 `单发价格 ÷ 修正后单发概率`（每击毁期望成本）升序，平局按 ID；仍受各单位交战规则约束，且只在"该单位仍来得及在目标到达前再交战"时让位（否则贵的也要打，防止便宜单位让位后目标突防）。
  - **C 由玩家逐单位设"交战优先级"数字**：最灵活，但增加部署界面负担（GDD 15 第 7 条规则编辑器已经很重）。
- 推荐：**B**（让位条件用 03 已有的解析拦截预测：便宜单位的最早可拦截时刻早于目标到达保护目标的时刻）。
- D3 验证：**可以**。纸面模拟一夜混编（Gepard + NASAMS + Patriot，对 Shahed + Kh‑101），比较 A / B 的交换比与突防数。
- 批准后改动：03 §3.2 分配步骤、Q-E9、对应测试用例；`data/rules/engagement.json`（03 新文件）增加 `allocation: "cheapest_expected"`；GDD / 数值表不改。

### B-T3-03 命中即毁 vs 游戏 HP

- 位置：03 §8.1 Q-I3、Q-E6（`roundsPerBurst`）；数值表 §2.1–2.3 的"游戏 HP"列；data `enemies/munitions.json`、`platforms.json` 的 `hp`。
- 背景：数值表 §3.3 给的是"单发基础拦截概率"；同时每种敌方单位都有游戏 HP（Shahed 2、Kh‑101 5、Tu‑22M3 14）。GDD 6.2 通用属性只列"单发拦截概率"。
- 选项：
  - **A 命中即毁、HP 只记录**（03 默认）：与数值表 §3.3 的概率口径一致、最简单、平衡只调一张表；代价是 HP 数据完全不起作用（需要在数值表注明"仅供将来使用"）。
  - **B 身管武器与碎片按 HP 扣减，导弹命中即毁**：让"高炮打 Kh‑101 要多次命中"更真实；但要给每种身管武器定"每次命中伤害"，并且 §3.3 中高炮概率的含义变成"命中率"，所有高炮数值需重标。
  - **C 所有武器按伤害 vs HP**：最复杂，与 §3.3 口径冲突最大。
- 推荐：**A**。HP 保留在数据中供战斗机机炮 / 将来扩展；数值表 §2 表头注明"游戏 HP：当前版本不参与拦截判定"。
- D3 验证：可以，但意义不大（A 是 B 的特例）；主要是范围决定。
- 批准后改动：数值表 §2.1–2.3 表头注释；03 Q-I3 关闭；`data/README.md` 说明 `hp` 字段未使用；GDD 不改。

### B-T3-04 指挥部信任度体系的形态与数值

- 位置：05 §8.1 全部 `trust.*`、`crossLevelModClamp`、`emergencySupport`、`requests[]`；§8.2 Q-E1、Q-E2、Q-E7、Q-E8、Q-F7；数值表 §1.6"信任度（大）"。
- 背景：GDD 9.2 信任度"用于申请增援"；GDD 13.3"信任度 → 下一关资源 ±10–20%"；GDD 9.5"信任度有下限"；GDD 12.3 第 6 关引入。GDD 同时把它写成"货币"和"评价"。
- 选项：
  - **A 货币 + 评价（05 默认）**：0–100，初值 50、下限 10；申请扣分（小 8 / 大 20）；开局按信任度给 ±10% 配额修正；夜内按交换比分档 −3…+3，单夜截断 −12/+8。花掉信任度 = 牺牲下一关配额，是有意的取舍。
  - **B 只读评价 + 阈值解锁**：信任度只决定"能申请什么"（≥ 60 可申请 NASAMS 等），申请不扣分、每关限次。规则简单、不会因申请而"越用越穷"；但削弱了 GDD 9.2"用信任度换增援"的交易感。
  - **C 纯货币**：不影响下一关配额，只用于申请。最简单，但 GDD 13.3 的跨关影响需改由奖励卡承担。
- 推荐：**A**，但把"申请扣分"与"开局修正"的上限一起写进平衡目标（D4 检查"一直申请"与"从不申请"两条策略的总资源差 ≤ 15%，防止出现统治策略）。Q-E2（按武器聚合判浪费）、Q-E7（AB 关两线都变化、申请指定付款线）、Q-F7（失败扣分重试不恢复）按 05 默认。
- D4 验证：**可以且必须**。用 D4 跑三种玩家画像（节省型 / 正常 / 挥霍型）× 18 关的信任度轨迹，检查是否触底、是否滚雪球。
- 批准后改动：05 §1.2、§3.4、§8；`data/rules/economy.json`（`trust` 块）；数值表 §1.6 / §4 第 1 条补"信任度量表 0–100"；GDD 9.2 补一句"申请消耗信任度"。

### B-T3-05 敌方 AI 的信息边界与高暴露度的后果

- 位置：04 §8.1 Q-A1、Q-A2、Q-A8、Q-A9、Q-A10、Q-A11；02 §8.1 Q39；数值表 §3.4 后果表；GDD 7.4。
- 背景：GDD 7.4"猎杀：暴露度 ≥ 70 进入已知目标清单，次夜遭定点打击"；数值表 §3.4"≥ 40 当夜反辐射导弹优先锁定；≥ 70 次夜进入清单；**100 当夜即遭定点打击**"。04 默认"不动态追加打击"，于是若关卡没有写 `known_targets` / `air_defense` 组，**暴露度 100 没有任何后果**，与数值表矛盾；暴露度体系（支柱之一）的牙齿取决于关卡作者是否记得写这类组。
- 选项：
  - **A 04 默认**：敌方可读暴露度、知道清单中单位的类型；100 不动态追加，全靠关卡数据。信息边界清楚，但 100 档可能失效。
  - **B 动态追加**：暴露度达 100 时注入 1 组 `precisionStrike { munitionId, count, delayGameSec }`。后果明确；但 AI 凭空增加敌人，破坏"波次数量由设计者控制"，也让平衡更难。
  - **C 改派（推荐）**：不新增敌人；暴露度达 100 时，把本夜**尚未生成**的 `weighted_random` 组中按 `retargetFrac`（默认 0.25，至少 1 枚）的弹药改为打该单位（优先选弹种匹配 `deception.attracts` 的组：伊斯坎德尔 / Lancet / Geran）。若本夜已无未生成的组，则写入 `CarryOut.KnownTargets` 并标"优先"，次夜生效。
- 推荐：**C**；信息边界按 A（可读暴露度与单位类型，假发射车按 `fakeLauncherAssumedRangeKm = 10`，不读其他真值）。
- D3 验证：**可以**。纸面模拟一夜：Patriot 常开到 100，比较 A / C 下的被打击次数与玩家其他目标的损失变化。
- 批准后改动：04 §3（`EnemyIntelRules`、钩子）、Q-A1；01 §3.1（注入 / 改派钩子，与 04 B-01 一并对齐）；`data/rules/enemy_ai.json`（04 新文件）增加 `exposure100 { retargetFrac, preferAttracts }`；数值表 §3.4"100"行补"（改派本夜未出发的打击）"；GDD 不改。

### B-T3-06 夜间可部署 / 转移的范围

- 位置：00 §8 Q17；04 §8.1 Q-D1、Q-D2、Q-D3、Q-D4、Q-D5、Q-D6、Q-D7、Q-D8；02 §8.1 Q19；05 §8.2 Q-F6；06 §8.4 B5。
- 背景：GDD 5.2 夜间可用操作：调动机动单位（火力组、拦截无人机班组）、紧急转移一个单位（仅展开时间按分钟计的系统），**没有"新部署"**；GDD 11.3"转移到新阵地首夜 −30%"；数值表 §3.5 触发规则"开火后转移到备用阵地"。
- 选项：
  - **A 04 默认（推荐）**：夜间不能从预备队新部署；`MoveUnit` 只限 `instant` 档（火力组、拦截无人机班组、单兵）、直线匀速只检查终点；`RelocateUnit` 限 `instant` / `minutes` 档，可去备用阵地；小时档不能转移；探测 / 电子战 / 欺骗单位只能原地撤收 / 展开；"开火后转移"触发规则不受档位限制、不耗点；原地撤收 1 点、原地展开 0 点。
  - **B 允许夜间新部署预备队（耗 2 点）**：更"街机"、容错高；但削弱 GDD 5.1"部署占 70% 决策"的定位，且 02 / 03 需要运行时初始化入口（04 B-06）。
  - **C A + 探测 / 电子战单位可转移**：给数据加 `moveSpeedKmh`；增加夜间操作面，但多数雷达展开以分钟 / 小时计，实际意义有限。
- 推荐：**A**。补一条澄清：小时档单位设了"开火后转移"时，夜间会撤收并在当夜剩余时间失去战斗力（这是玩家战前的自愿选择，界面需提示）。
- D3 验证：部分可以（伏击打法"静默 → 开机 → 撤收"的收益），主要是范围决定。
- 批准后改动：04 §3.4 / §8；00 Q17 关闭；06 B5 关闭；`data/rules/commands.json`（04 新文件）的 `commandPointCosts`；GDD 5.2 补一句"夜间不能新部署"。

### B-T3-07 自动结算"略逊于亲自指挥"的实现

- 位置：00 §8 Q11；05 §8.1 `autoResolve.*`，§8.2 Q-F3、Q-F4、Q-F8，§8.3 R-00-9。
- 背景：GDD 11.5"自动结算略逊于亲自指挥；玩家随时可选择亲自观看（少量奖励）"；GDD 11.6 第 5 条把"自动 / 亲自比例"作为时长旋钮。惩罚太大 → 玩家被迫每夜亲自打（时长失控）；太小 → 关键夜以外没人亲自打也无所谓（可接受）。
- 选项：
  - **A 05 默认**：三项叠加——不用指挥点（无二选一、无手动支援）+ 拦截概率 ×0.95 + 暴露 ×1.0；观看奖励信任度 +1；自动结算夜 `Defeated` 不算关卡失败；`survive_nights` 只计关键夜。
  - **B 只靠"不用指挥点"自然产生差距（推荐起点）**：不加数值惩罚（×1.0）；若 WS09 测得差距 < 3%，再启用 ×0.95。结构上更干净（模拟层不需要"自动模式"分支），且符合"略逊"。
  - **C 固定大惩罚 ×0.85**：强推亲自指挥，与 GDD 11.6 的时长控制意图冲突。
- 推荐：**B**（`autoResolve.interceptProbMult` 默认 1.0、字段保留），其余按 A（Q-F3 不算失败、Q-F8 只计关键夜、修正走 `CarryIn.AutoResolve`）。平衡目标：`AutoResolveGap`（亲自 − 自动的加权损失差）落在 3–10%。
- D4 验证：**可以**（同一夜分别以"自动"与"亲自（脚本化指挥点使用）"跑 N 种子，测差距）。
- 批准后改动：05 §1.2 `autoResolve`、§3.8.2、§1.3 `balanceTargets`；`data/rules/campaign.json`（05 新文件）；00 Q11 关闭；GDD 不改。

### B-T3-08 电子战的落点偏移、判定次数与 AI 视觉制导

- 位置：02 §8.1 Q8、Q9、Q10、Q11、Q12；03 §8.3 B4；数值表 §1.4、§3.1、§5.3"落点偏移：暂取 +2 格；1.4 与 3.1 以哪条为准在 WS01-015 确认"；GDD 7.2"精度受电子战（**降档**）…影响"、8.3、数值表 §4 第 5 条。
- 背景：GDD 8.3"电子战不摧毁目标，只降低精度或切断控制"；数值表 §4"电子战单独使用无法守住关卡，但能显著降低有效命中"。三处写法：GDD 7.2 说"降档"；数值表 §3.1 说"按精度档 +1 / +2 格"；§1.4 / data `offsetCellsAdd: 2`。另有 data `national_gnss_spoof.accuracyTierDrop: 2`。
- 选项：
  - **A 02 默认（推荐）**：单位电子战按 §3.1 `ewExtraCells[原精度档]`（A/B +1、C/D +2），不降档；国家级导航欺骗按 data `accuracyTierDrop 2`（降档后取新档偏移，**与单位电子战取较大者，不叠加**）；效能概率每个目标每类效果只掷一次并锁存到夜末；链路中断坠落不造成地面伤害；AI 视觉型（`aiVisionFrom`）对区域导航干扰免疫、对导航欺骗 ×0.5。
  - **B 统一"降档"**（GDD 7.2 字面）：单位电子战降 1 档、国家级降 2 档。与 Orlan 升档对称、概念统一；但 A 档目标（无偏移）降到 B 档只得到 0–1 格随机偏移，比 §3.1 的 +1 弱。
  - **C 固定 +2 格**（§5.3 暂定值、data `offsetCellsAdd`）：最简单，但不区分精度档。

### B-T3-09 "生成即投弹"的平台（Tu‑22M3、MiG‑31K、Su‑24M/Su‑34 带 Kh‑59）能否被打

### B-T3-10 辐射策略的"暴露系数"是否在模拟中相乘

- 位置：02 §8.1 Q6、Q7、Q18；数值表 §3.5 策略表"暴露系数 ×1.0 / ×0.6 / ×0.4 / ×0.2 / ×0.5"、§1.3"有指示时暴露 ×0.3"；data `emission.json strategies[].exposureMult`、`tracks.json cueing.*.exposureMult`。
- 背景：GDD 8.2 暴露度（0–100）是"辐射策略与反防空压制"支柱的核心反馈；数值表 §3.5 的系数是人工审核过的设计值。02 默认**不相乘**：模拟真实开关机（按预警开、间歇开 1/1 游戏秒……），暴露只在"开机"时按基础速率累积，策略差异由开机时长自然产生；系数只用于界面与自动结算估算。
- 选项：
  - **A 不相乘、由开关机自然产生（02 默认，推荐）**：机制自洽、无重复计算；但最终比例取决于夜晚节奏，可能与 ×0.6 / ×0.4 / ×0.2 偏离很大（例如"按预警开机"在密集夜几乎一直开 → 接近 ×1.0）。
  - **B 两者都要**：真实开关机 + 开机时再乘系数。会重复计算（"静默待机"最后时刻才开机，再 ×0.2 就几乎不暴露）。
  - **C 不模拟开关机对暴露的影响，暴露 = 基础速率 × 系数（只要单位处于"工作"状态）**：数值完全按表，但"关机越早越安全"（GDD 8.2）与反辐射导弹关机时机规则失去依托。
- 推荐：**A**，并把数值表 §3.5 的系数改称"**目标平均系数**（平衡目标）"；D3 必须验证在典型夜晚中各策略的实测比例落在表值 ±0.15 内，偏离时调整 `dutyCycleDefaultOn/Off`、`decoyLeadGameSec` 等参数，而不是改为相乘。Q7（静默 −0.5 只在本步无任何正向来源时生效）按 02 默认。
- D3 验证：**可以且必须**（本条的推荐以验证结果为前提）。
- 批准后改动：02 §3（暴露累积）、Q6；数值表 §3.5 表头"暴露系数"→"目标平均暴露系数"并加注；`data/rules/emission.json` `_source` 注明系数为平衡目标；`tools/balance`（WS06）增加该统计；GDD 不改。
